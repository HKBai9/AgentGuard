# 必要性论证与产品化路线

> 回答两个问题：
> 1. **主流 Agent 自己就带 guard，我们做这个实验还有必要吗？**
> 2. **怎么把它做成一个产品（App 形态）？**

---

# 第一部分：为什么仍然有必要

## 一、先纠正一个前提：主流 Agent 的 guard 长在"错误的位置"

"主流 Agent 自带 guard"是真的，但要分清它们各自是什么：

| 产品 / 框架 | 自带的安全机制 | 粒度 | 强制力 |
|---|---|---|---|
| Claude Code | 工具调用前的**交互式确认弹窗** | 单次调用，靠人点"同意" | 有人盯着时有效 |
| Cursor | 命令白名单 + 弹窗 | 按**命令名**粗粒度 | 可被 `curl`/`python` 绕过 |
| Codex CLI | 沙箱模式（read-only / workspace-write）+ 审批 | 会话级 | 粒度粗，非资源级策略 |
| OpenHands | 运行时容器隔离 | 进程级 | 强，但不表达业务授权边界 |
| LangChain / LangGraph | `human_in_the_loop` 中间件 | 工作流节点 | 需自己写策略 |
| 各厂商模型层 | RLHF 对齐 + 输入输出过滤 | 文本层 | **无否决权**（见 `docs/COMPETITIVE_EDGE.md`） |

**共性是：这些机制要么依赖"有人看着"，要么依赖"工具叫什么名字"。**
它们都不解决这个问题：

> **Agent 能不能用被允许的工具，去做被禁止的事？**

## 二、实测：工具名白名单在原理上就守不住

`python experiments/run_bypass_demo.py` —— 同一个越权目标（访问内网数据库），
两种走法，三组防护：

| 分组 | `ssh_connect(internal-db)` | `run_command("curl -v http://internal-db/")` |
|---|---|---|
| 组1 无防护 | 🔴 连上内网 | 🔴 连上内网 |
| **组2 主流式 guard（仅工具名白名单）** | ⛔ 拦住（名字被禁） | 🔴 **连上内网（名字被允许）** |
| 组3 本作品（资源级判定） | ⛔ 拦住 | ⛔ **拦住** |

**组2 被绕过、组3 拦住。**

为什么组2 必然被绕过？因为几乎所有 Agent 都必须开放**万能工具**
（`run_command` / `bash` / `python`）——否则它什么都干不了。
而一旦开放，Agent 就能用它们去做任何被单独禁止的事：

```
被禁: ssh_connect internal-db
绕过: run_command "curl http://internal-db:3306/"
绕过: run_command "python -c \"import socket; socket.create_connection(('internal-db',3306))\""
绕过: run_command "bash -c 'cat < /dev/tcp/internal-db/3306'"
```

组3 之所以守得住，是因为它**不看工具名，看参数**：
从命令字符串里解析出目标主机与端口，再比对网络策略。
这件事"工具名白名单"在原理上做不到。

> **可以直接对评委说的话：**
> "我们不是做了一个比主流 Agent 更好的 guard，
>  而是指出主流 guard 放错了层——它长在 Agent 进程内、按工具名判定，
>  因此可以被 Agent 自己绕过。我们把它挪到了 Agent 外部的强制层。"

## 三、还有三个主流方案在结构上无法提供的能力

### 3.1 跨厂商、跨框架的统一策略

企业的现实是：同一家公司里同时跑着 Claude Code、内部 LangGraph Agent、
采购的第三方 Agent。每个都有自己的权限配置，**策略无法统一、审计无法汇总**。
我们做的是**模型无关、框架无关的独立控制面**（`ToolBridge` 是唯一接入点），
一份 `permission_baseline.yaml` 管所有 Agent。

### 3.2 非交互场景（这是最硬的需求）

交互式弹窗的前提是"有人盯着"。但真实部署里大量 Agent 是**自主运行**的：

- 夜间批量漏洞扫描；
- 几十个并发会话的代码审计；
- 7×24 安全巡检。

**没有人会去点"允许"。** 这些场景下必须有一层不依赖人类的强制策略。

### 3.3 可审计、可合规

- 交互式弹窗是**决策**，不留策略级别的证据；
- 我们输出的是**策略 + 证据链**：规则 ID、层级、严重度、证据 JSON、
  完整动作历史，落盘 `audit.jsonl`。

安全评审问"你凭什么保证它不会读私钥"：
- 答"我让模型别读" → 不合格；
- 答"策略引擎在工具调用点强制校验，这里有 59 项回归测试、规则 ID 和审计日志" → 合格。

## 四、诚实地说：这个方向已经有人在做了

不能假装这是无人区。相关方向确实有玩家：

| 方向 | 代表 |
|---|---|
| Agent 可观测 / 追踪 | LangSmith、Langfuse、Arize |
| LLM 输入输出护栏 | NVIDIA NeMo Guardrails、Guardrails AI、Lakera |
| Agent 身份与权限 | 各云厂商的 agent identity 服务（如 AWS Bedrock AgentCore） |
| MCP 安全 | MCP 生态里的安全网关类项目 |

**这对我们是好事，不是坏事**——它证明这个需求真实存在、有市场。
但要说清我们的差异：

- 上面多数做的是**输入输出内容过滤**（拦"话"）或**可观测**（记录"发生了什么"）；
- 我们做的是**工具调用层面的执行前拦截 + 资源级策略**（拦"事"），
  而且强调两个特性：**非绕过性**（在 Agent 外部）与**时序行为链**
  （跨步骤识别"读凭证→连内网"）。

> 定位一句话：
> **别人在做"Agent 说了什么"的护栏，我们做"Agent 做了什么"的断路器。**

# 第二部分：产品化路线（App 形态）

## 五、为什么必须是"外部网关"形态——这是产品的基石

如果防护层作为一个 Python 库被 Agent 引入（就是我们现在 demo 的形态），
那它**仍然在 Agent 进程内**。一个被完全控制的 Agent 理论上可以：
跳过这个库直接调用底层 HTTP、或者改写自己的策略文件。

**做产品必须把控制点移出 Agent 进程。** 而这件事在今天有一个天然落点：
**MCP（Model Context Protocol）**。

MCP 已经是主流 Agent 调用外部工具的事实标准。Agent 通过 URL 连接 MCP Server：

```
Agent  ──MCP──▶  tools-server          （现状：Agent 直连工具）
Agent  ──MCP──▶  ★ AgentGuard Gateway ──MCP──▶  tools-server   （产品形态）
```

**接入成本 = 改一行配置**（把工具服务器的 URL 指向网关）。
而 Agent 进程里**没有任何代码**能绕过它——因为工具本身在网关后面。

这就是产品化的核心洞察：

> **把"防护"从一个库，变成一个 Agent 必须经过的代理。**

## 六、产品形态设计

### 6.1 产品名与定位

**AgentGuard · Agent 工具调用安全网关**

一句话：*把企业 AI Agent 的每一次工具调用，变成一条可审、可控、可回溯的策略决策。*

类比（方便评委理解）：
- 它是 **Agent 的 WAF** —— 但拦的不是 HTTP 攻击载荷，是 Agent 的越权动作；
- 它是 **Agent 的 API 网关** —— 统一策略、统一审计、统一配额；
- 它是 **Agent 的 egress proxy** —— 所有出站动作的强制检查点。

### 6.2 架构

```
┌─────────────────────────────────────────────────────────────┐
│  控制台 (Web App)                                            │
│  策略编辑 · 实时告警 · 会话回放 · 审计报表 · 审批工作流        │
└───────────────┬─────────────────────────────────────────────┘
                │ REST / WebSocket
┌───────────────▼─────────────────────────────────────────────┐
│  AgentGuard Gateway  (核心服务)                              │
│  ┌─────────────┐ ┌─────────────┐ ┌──────────────────────┐  │
│  │ MCP Proxy   │ │ Policy      │ │ 时序行为链引擎        │  │
│  │ 拦截所有工具 │ │ Engine (L1) │ │ (L3, 跨步骤状态机)    │  │
│  │ 调用        │ │             │ │                      │  │
│  └─────────────┘ └─────────────┘ └──────────────────────┘  │
│  ┌─────────────┐ ┌─────────────┐ ┌──────────────────────┐  │
│  │ 语义意图校验 │ │ 阻断 / 隔离  │ │ 审计存储 + 回滚快照   │  │
│  │ (L2)        │ │ / 回滚 (L4) │ │                      │  │
│  └─────────────┘ └─────────────┘ └──────────────────────┘  │
└───────────────┬─────────────────────────────────────────────┘
                │ MCP
     ┌──────────┼──────────┬──────────────┐
     ▼          ▼          ▼              ▼
  文件工具   Shell工具   数据库工具    内部 API 工具
```

### 6.3 五个核心能力（产品的"销售点"）

| # | 能力 | 客户价值 | 当前 demo 状态 |
|---|---|---|---|
| 1 | **非绕过性** | 安全团队敢签字 | 需做 MCP Proxy（改造量中等） |
| 2 | **资源级策略** | 区分"curl 靶站"和"curl 内网" | ✅ 已实现并通过红队验证 |
| 3 | **时序行为链** | 抓住单步合规的组合越权 | ✅ 已实现（`SEQ-001/002/003`） |
| 4 | **审计与合规报表** | 过等保 / 应对内部审计 | 部分（JSONL 审计已实现，报表需补） |
| 5 | **多 Agent 统一治理** | 一份策略管所有 Agent | ✅ 策略与 Agent 解耦 |

### 6.4 最小可用产品（MVP）范围

> 判断标准：**能不能在一个真实企业里跑起来，并留下审计证据。**

**必须做（MVP）**
1. **MCP Proxy**：拦截 `tools/call`，把每次调用送进现有 `SandboxGuard`，再转发或拒绝；
2. **策略中心**：YAML/DB 存策略，提供 REST 读写 + 版本管理；
3. **审计存储**：JSONL → SQLite/Postgres，支持按会话/规则/时间检索；
4. **Web 控制台**：策略编辑、实时告警流、会话回放（把现有 Streamlit 页面升级）；
5. **审批工作流**：高危动作可配置"阻断"或"转人工审批"（补齐交互式场景）。

**暂不做**
- 多租户、RBAC（企业内网部署先单租户）；
- 句向量语义模型（先用现成的字符 n-gram + 词表，够用且零依赖）；
- 系统层（eBPF/seccomp）下沉 —— 这是 v2，先把应用层做扎实。

**技术选型建议**：核心引擎已经是纯标准库 Python（`agentguard/`），
网关用 FastAPI + 官方 MCP SDK；控制台从 Streamlit 迁到 React 或保持 Streamlit 起步。

### 6.5 交付形态

| 形态 | 适用 | 说明 |
|---|---|---|
| **自托管 Docker Compose**（首发） | 企业内网、私有化要求高 | 一个 compose 起网关+控制台+DB，客户自己拿策略文件 |
| Helm Chart | 已有 K8s 的团队 | 复用 compose 的镜像 |
| SaaS（后期） | 中小客户 | 只在客户侧部署一个轻量 egress agent 回连 |

首推**自托管**：安全产品卖给安全团队，私有化是刚需，也回避了"把 Agent 流量
送到第三方"的信任问题。

## 七、商业化路径

### 7.1 目标客户（按优先级）

**第一优先：已经有多个内部 Agent、且过不了安全评审的企业平台团队**

为什么是它：
- 痛点最硬 —— 内审/合规一票否决，是**必须买**而不是"锦上添花"；
- 已有多 Agent，**统一治理**需求真实存在，单点方案满足不了；
- 有预算（平台团队），决策链短。

典型场景：金融/运营商的内部 AI 平台，跑着自研 LangGraph Agent +
采购的编码 Agent，要求"所有 Agent 的工具调用必须留痕、越权必须阻断"。

**第二优先：做 Agent 产品的厂商（OEM 集成）**
把 AgentGuard 作为"安全版"卖给 Agent 厂商，帮他们过客户的采购安全审查。
对厂商来说，这是把"安全"从自研成本变成采购项。

### 7.2 定价思路

按 **受管 Agent 会话数 / 月** 订阅（安全产品的常规模式），
自托管版按年授权 + 支持服务。对第一个客户可以免费换案例与背书。

### 7.3 从竞赛作品到产品的路线图

| 阶段 | 时间 | 目标 | 交付 |
|---|---|---|---|
| **P0 竞赛作品** | 现在 | 证明技术可行、有对照实验 | ✅ 已完成（本仓库） |
| **P1 原型产品** | 1–2 个月 | MCP Proxy + 控制台 + 审计库，能在真实 MCP 工具上跑通 | Docker Compose |
| **P2 首个客户** | 3–6 个月 | 找 1 家企业内网试点，用真实 Agent 流量打磨策略 | 私有化部署 + 案例 |
| **P3 产品化** | 6–12 个月 | 审批工作流、报表、K8s、多 Agent 治理 | 可售卖版本 |

### 7.4 这件事的"不可绕过性"还差什么（诚实评估）

必须承认：**只要防护在应用层，理论上就可能被绕过。** 所以产品路线里有一条硬指标：

```
v1（应用层，MCP Gateway）  →  拦住"守规矩的 Agent"和"被注入的 Agent"
v2（系统层，容器/seccomp/eBPF）→  拦住"完全失控的 Agent"
```

v1 已经能覆盖绝大多数真实风险（Agent 不会主动对抗自己的工具层，
它只是"被诱导做错事"），而 v2 是把不可绕过性做到极致。
**答辩时主动说这条演进路径，比声称"绝对安全"更可信。**

## 八、对竞赛的直接建议

1. **别把作品讲成"更好的 guard"**，要讲成"**guard 应该放在哪一层**"——
   我们给出了答案（Agent 外部、执行前、资源级），并做了实验证明放在 Agent 内部的
   工具名白名单会被绕过（`experiments/run_bypass_demo.py`）。
2. **不要声称市场空白**，要承认有玩家、说明差异（拦"话" vs 拦"事"）。
3. **产品化讲 MCP Gateway**，因为它是今天的真实接入点，且能一句话说清价值：
   *"改一行 URL，你的所有 Agent 就有了统一策略和完整审计。"*
4. **把红队数据当资产**（`docs/COMPETITIVE_EDGE.md`）：2/3 绕过提示词防护、
   工具名白名单被 `curl` 绕过 —— 这些是我们自己测出来的，不是引用别人的结论。
